# RAG 项目面试准备

## 一、项目一句话介绍

基于 RAG 架构的知识库问答系统，支持向量检索 + BM25 混合检索 + CrossEncoder 重排序，最终由 LLM 生成回答。核心能力是"知道自己不知道" — 对知识库外的问题能拒绝回答而不是瞎编。

---

## 二、架构全流程（必须能画出来）

```
用户提问
  ↓
Embedding (bge-base-zh) → 向量检索 (ChromaDB, cosine)
  +
jieba 分词 → BM25 关键词检索
  ↓
RRF 融合（Reciprocal Rank Fusion）
  ↓
CrossEncoder 重排序 (bge-reranker-base, GPU)
  ↓
Grounding 判断（有没有足够证据？）
  ├─ Yes → 拼 prompt + LLM 生成回答
  └─ No  → 返回"无法回答"
```

---

## 三、每个环节可能被问到的问题

### 3.1 文档切分（Chunking）

**Q: 你的 chunk 策略是什么？为什么这么切？**

先按段落（双换行）切，保持语义完整性。超过 chunk_size(800字符) 的段落再用滑动窗口切，overlap=120 字符保证上下文连贯。

**Q: chunk_size 怎么定的？大了小了分别有什么问题？**

- 太大：一个 chunk 里混了多个话题，检索时相关性被稀释，precision 下降
- 太小：上下文不够，LLM 拿到的片段缺乏完整信息，生成质量差
- 800 是经验值，对中文技术文档比较合适。实际应该根据文档特点调

**Q: overlap 的作用？**

防止关键信息刚好被切在边界上。比如一个概念的定义在第一个 chunk 末尾，解释在第二个 chunk 开头，没有 overlap 就断了。

> 深挖风险：可能追问"你试过不同的 chunk_size 吗？有没有做过对比实验？"
> 应对：可以说做了消融实验，800 在当前数据集上 recall 最高，但承认数据集小（35条），不够严谨

### 3.2 Embedding 模型

**Q: 为什么选 bge-base-zh 而不是 OpenAI 的 embedding？**

- 开源，不依赖外部 API，延迟可控
- 中文专用，对中文语义理解比通用多语言模型好
- 768 维，存储和计算成本适中

**Q: 你换过模型吗？效果差多少？**

换过。一开始用 all-MiniLM-L6-v2（英文小模型，22M参数），vector_only 的 recall@3 只有 0.74。换成 bge-base-zh-v1.5（102M参数，中文专用）后涨到 0.94。说明 embedding 模型对召回质量影响很大，尤其是语言匹配。

**Q: cosine 和 euclidean 距离有什么区别？为什么选 cosine？**

- cosine 衡量方向相似度，不受向量长度影响。两段语义相近但长度不同的文本，cosine 相似度高
- euclidean 衡量绝对距离，受向量大小影响
- sentence-transformers 输出的向量已经做了归一化，用 cosine 更合理

> 深挖风险：可能问 HNSW 索引原理
> 要点：分层的可导航小世界图，O(log n) 近似最近邻搜索。每层是一个跳表结构，上层稀疏用于快速定位，下层密集用于精确搜索。不需要背公式，能说清"分层 + 贪心搜索"就行

### 3.3 BM25

**Q: BM25 是什么？为什么要加 BM25？**

BM25 是基于词频的经典检索算法。核心思想：一个词在某篇文档里出现得多（TF 高），但在整个语料库里出现得少（IDF 高），那这个词对这篇文档的区分度就高。

向量检索擅长语义匹配（"快速" ≈ "高性能"），但对精确关键词匹配不敏感。BM25 擅长精确匹配（搜"Redis"就找含"Redis"的文档），但不懂语义。两者互补。

**Q: BM25 的公式能说一下吗？**

```
score(q, d) = Σ IDF(qi) * (tf * (k1 + 1)) / (tf + k1 * (1 - b + b * dl/avgdl))
```

- IDF：逆文档频率，越稀有的词权重越高
- tf：词频
- k1=2.0：控制词频饱和度，k1 越大，高频词的边际收益越高
- b=0.75：长度归一化，b=1 完全按长度惩罚，b=0 不惩罚
- dl/avgdl：文档长度 / 平均文档长度

**Q: 中文分词用的什么？**

jieba。中文没有空格分隔，必须先分词才能做 BM25。比如"机器学习"要切成"机器"+"学习"，不然整个词匹配不上。

> 深挖风险：可能问"jieba 的分词原理"
> 要点：基于前缀词典 + 动态规划找最大概率路径，对未登录词用 HMM（隐马尔可夫模型）。不需要深入 HMM 细节，知道"词典 + 统计"就行

### 3.4 混合检索与 RRF 融合

**Q: 为什么用 RRF 而不是直接把两个分数加起来？**

因为两个检索器的分数量纲完全不同：
- 向量检索：cosine distance，0~2 之间
- BM25：tf-idf 加权分数，可能是 0~20

直接加权求和需要先归一化，而归一化方式的选择本身就是个问题。RRF 只看排名不看分数：

```
RRF_score(d) = Σ weight / (k + rank)
```

rank 是文档在各个检索器中的排名，k=60 是平滑参数。这样不管原始分数是什么量纲，融合结果都是可比的。

**Q: k=60 是怎么定的？**

论文里的默认值。k 越大，不同排名之间的分数差距越小（更平滑）；k 越小，排名靠前的文档优势越大。60 是经验值，大部分场景不需要调。

**Q: RRF 有什么缺点？**

- 丢失了分数的绝对信息。一个文档在向量检索里 score=0.99（非常相关）和 score=0.51（勉强相关）只要排名一样，RRF 分数就一样
- 所以后面需要 rerank 来补偿这个信息损失

### 3.5 Rerank（重排序）

**Q: CrossEncoder 和 Bi-Encoder 有什么区别？**

这是高频考点：

| | Bi-Encoder | CrossEncoder |
|---|---|---|
| 输入 | query 和 doc 分别编码 | query + doc 拼接后一起编码 |
| 输出 | 两个向量，算相似度 | 直接输出相关性分数 |
| 速度 | 快（可以预计算 doc 向量） | 慢（每对都要过一遍模型） |
| 精度 | 较低 | 高（能捕捉 query-doc 交互） |
| 用途 | 召回阶段（从百万文档里选几十个） | 精排阶段（从几十个里选最好的几个） |

所以架构是：Bi-Encoder 做粗筛（快但粗），CrossEncoder 做精排（慢但准）。

**Q: 为什么用 sigmoid 归一化而不是 min-max？**

- sigmoid 保留了绝对语义信息：logit=5 → 0.993（非常相关），logit=0 → 0.5（不确定），logit=-5 → 0.007（不相关）
- min-max 只有相对排名信息：batch 里最高分永远是 1.0，即使所有文档都不相关
- grounding 判断需要的是"这个文档到底相不相关"的绝对判断，所以 sigmoid 更合适

**Q: rerank 的性能问题怎么解决的？**

一开始跑在 CPU 上，35 条数据 rerank 耗时 55 秒。原因是 RTX 5060 用 Blackwell 架构，PyTorch 稳定版不支持。换了 PyTorch nightly (CUDA 12.8) 后降到 5 秒。如果模型常驻内存（生产环境），单次查询 < 1 秒。

> 深挖风险：可能问"还能怎么优化 rerank 速度？"
> 应对：
> - 导出 ONNX + TensorRT 推理（2-3x 加速）
> - 减少候选数量（fetch_k 从 6 降到 4）
> - 模型蒸馏（用大模型的 rerank 结果训练小模型）
> - 量化（FP16 / INT8）

### 3.6 Grounding（置信度判断）

**Q: 怎么判断检索结果够不够好？**

三个条件同时满足才算 grounded：
1. top_score >= 0.65（最相关的那条够不够相关）
2. average_score >= 0.5（整体质量）
3. 至少 1 条 score >= 0.4（不能全是噪声）

**Q: 阈值怎么定的？**

通过分析正负样本的分数分布：
- 负样本（知识库里没有的话题）：sigmoid 后 top_score 在 0.50~0.53
- 正样本：top_score 在 0.72+
- 中间有 0.53~0.72 的间隔，取 0.65 作为分界线

**Q: 你遇到过什么 grounding 相关的 bug？**

这是项目最有价值的踩坑经历：

一开始 hybrid 模式的 grounding 只有 0.11（几乎全判错）。排查发现是 score 量纲问题 — 阈值 0.5 是按向量检索的 0~1 分数设计的，但 RRF 融合后的分数只有 0.01~0.03，永远过不了 0.5。

解决方案是在 score 产生的源头做归一化：RRF 用 min-max，rerank 用 sigmoid。统一到 0~1 后阈值才能正常工作。

还踩了一个坑：改了 config.py 的默认值但 `.env` 里写死了旧值。pydantic-settings 的优先级是 `.env` > 默认值，所以改了等于没改。

## 四、Eval 相关

**Q: 你的评估指标有哪些？分别衡量什么？**

| 指标 | 含义 | 衡量什么 |
|------|------|---------|
| Recall@K | 前 K 条里有没有正确文档 | 能不能找到 |
| MRR | 正确文档排名的倒数的均值 | 排得准不准 |
| Precision@K | 前 K 条里有多少是相关的 | 噪声多不多 |
| Keyword Hit | 返回文档是否包含预期关键词 | 内容对不对口 |
| Grounding | 系统判断"有没有证据"的准确率 | 知不知道自己不知道 |

**Q: 你的消融实验结果？**

| Config | Recall@3 | MRR | P@3 | Grounding | 耗时 |
|--------|----------|-----|-----|-----------|------|
| vector_only | 0.94 | 0.92 | 0.79 | 0.43 | 0.6s |
| hybrid | 0.97 | 0.94 | 0.78 | 0.49 | 0.8s |
| hybrid+rerank | 0.97 | 0.91 | 0.82 | 0.94 | 4.6s |

每个组件的贡献：
- +BM25：recall 从 0.94 → 0.97，MRR 从 0.92 → 0.94（关键词匹配补充了语义检索的盲区）
- +Rerank：precision 从 0.78 → 0.82，grounding 从 0.49 → 0.94（精排大幅提升置信度判断）

**Q: 数据集多大？够吗？**

35 条，包含 30 个正样本和 5 个负样本。坦白说不够大，一条判错就是 3% 的波动。理想情况应该扩到 100+ 条，覆盖更多边界 case（比如跨文档问题、模糊问题、部分相关问题）。

## 五、工程踩坑（面试加分项）

### 5.1 pydantic-settings 配置优先级
`.env` > 环境变量 > Field(default=...)。改了代码里的默认值但 `.env` 没改，等于白改。

### 5.2 lru_cache 导致配置不刷新
`get_settings()` 用了 `@lru_cache`，eval 脚本切换配置后必须 `cache_clear()`，否则拿到的还是旧配置。

### 5.3 GPU 兼容性
RTX 5060 (Blackwell, sm_120) 需要 PyTorch nightly + CUDA 12.8。稳定版不支持新架构。

### 5.4 rerank_top_n 截断
rerank_top_n < top_k 时，rerank 后的结果比原始检索还少。用 `max(rerank_top_n, top_k)` 兜底。

## 六、可能的延伸问题

**Q: 如果文档量从几十篇涨到几万篇，架构要怎么改？**
- ChromaDB 换成 Milvus / Qdrant（分布式向量数据库）
- BM25 换成 Elasticsearch
- Embedding 和 Rerank 模型部署为独立服务（Triton Inference Server）
- 加缓存层（热门问题缓存检索结果）

**Q: 如果要支持多轮对话怎么做？**
- 对话历史拼接到 query 里做检索
- 或者用 LLM 先做 query rewriting（把多轮对话压缩成一个独立问题）

**Q: 如何处理文档更新？**
- 增量 ingest：只处理新增/修改的文档（通过文件 hash 判断）
- 删除旧 chunk，插入新 chunk
- BM25 索引需要重建（或用支持增量更新的实现）

**Q: RAG 的局限性？**
- 检索质量是天花板，检索不到的信息 LLM 也生成不了
- chunk 切分可能破坏上下文完整性
- 对需要跨多个文档推理的问题效果差
- 延迟比纯 LLM 高（多了检索 + rerank 的开销）
