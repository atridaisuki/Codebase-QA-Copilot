# AI 应用开发基础概念指南

> 面向后端开发者的 AI 应用技术全景，帮你搞清楚这些工具/框架/概念到底是干什么的、什么时候该用。

---

## 1. 先搞清楚一张大图

AI 应用开发大致可以分成这几层：

```
┌─────────────────────────────────────────────────┐
│                  应用层（你要做的东西）              │
│   聊天机器人 / 代码助手 / 知识问答 / Agent 工作流    │
├─────────────────────────────────────────────────┤
│                 编排层（框架和工具）                 │
│   LangChain / LlamaIndex / Dify / CrewAI        │
├─────────────────────────────────────────────────┤
│                 能力层（核心技术模式）               │
│   RAG / Agent / Function Calling / Fine-tuning   │
├─────────────────────────────────────────────────┤
│                 模型层（大语言模型）                 │
│   GPT-4 / Claude / Llama / Qwen / DeepSeek      │
├─────────────────────────────────────────────────┤
│                 基础设施层                         │
│   向量数据库 / 推理引擎 / GPU 集群                  │
└─────────────────────────────────────────────────┘
```

作为后端 + AI 方向，你主要活动在**应用层和编排层**，需要理解能力层的原理，但不需要自己训练模型。

## 2. 核心技术模式（能力层）

### 2.1 RAG（Retrieval-Augmented Generation，检索增强生成）

**一句话：** 先从知识库里搜相关内容，再把搜到的内容喂给 LLM，让它基于这些内容回答问题。

**为什么需要它：**
- LLM 的知识有截止日期，不知道你公司内部的文档
- 直接问 LLM 它会"编"（幻觉问题）
- RAG 让 LLM 的回答有据可查

**流程：**
```
用户提问
  ↓
[Embedding 模型] → 把问题变成向量
  ↓
[向量数据库] → 搜索最相似的文档片段
  ↓
[拼接 Prompt] → "根据以下资料回答问题：{搜到的内容}\n问题：{用户问题}"
  ↓
[LLM] → 生成有依据的回答
```

**你现在的项目就是一个 RAG 系统。**

**关键概念：**
- **Embedding（嵌入/向量化）**：把文本变成一组数字（向量），语义相近的文本向量距离也近
- **Chunk（切片）**：文档太长塞不进 LLM，需要切成小段。怎么切很有讲究（按段落、按语义、按 token 数）
- **向量检索**：在向量数据库里找和问题最相似的 chunk
- **Reranker（重排序）**：初步检索后用更精确的模型重新排序，提高相关性

**进阶玩法：**
- 多路召回：向量检索 + BM25 关键词检索，结果融合
- 知识图谱增强：不只是文本片段，还有实体关系
- 自适应检索：根据问题类型决定要不要检索、检索多少

---

### 2.2 Agent（智能体）

**一句话：** 让 LLM 不只是回答问题，而是能**自主决策、调用工具、完成多步骤任务**。

**和普通 LLM 调用的区别：**
```
普通调用：用户问 → LLM 答 → 结束
Agent：  用户给任务 → LLM 思考 → 决定调什么工具 → 执行 → 观察结果 → 继续思考 → ... → 任务完成
```

**核心循环——ReAct（Reasoning + Acting）：**
```
循环开始：
  1. Thought（思考）：我需要做什么？当前进展如何？
  2. Action（行动）：决定调用哪个工具，传什么参数
  3. Observation（观察）：工具返回了什么结果
  4. 判断：任务完成了吗？
     - 没完成 → 回到第 1 步
     - 完成了 → 输出最终结果
```

**举个例子：**
> 用户："帮我查一下北京明天的天气，如果会下雨就帮我发一封提醒邮件"

Agent 的执行过程：
1. **Thought**：我需要先查天气
2. **Action**：调用天气 API → `get_weather("北京", "明天")`
3. **Observation**：明天小雨，15°C
4. **Thought**：会下雨，需要发邮件
5. **Action**：调用邮件工具 → `send_email(subject="明天带伞", body="北京明天小雨")`
6. **Observation**：邮件发送成功
7. **Final Answer**：已查询天气并发送提醒邮件

**关键概念：**
- **Tool / Function Calling**：LLM 输出结构化的工具调用指令，后端执行后把结果返回给 LLM
- **Planning（规划）**：复杂任务先拆解成子步骤
- **Memory（记忆）**：短期记忆（当前对话上下文）+ 长期记忆（跨会话的知识存储）
- **Self-reflection（自我反思）**：执行出错时能分析原因、调整策略

---

### 2.3 Function Calling（函数调用）

**一句话：** 让 LLM 以结构化 JSON 的方式告诉你"我想调用哪个函数、传什么参数"。

**它不是 LLM 自己执行代码**，而是：
```
你告诉 LLM → "你有这些工具可以用：[搜索, 计算器, 发邮件]"
LLM 回复   → {"tool": "搜索", "args": {"query": "北京天气"}}
你的后端    → 真正执行搜索，把结果返回给 LLM
LLM 再回复  → 基于搜索结果生成自然语言回答
```

**和 Agent 的关系：** Function Calling 是 Agent 的基础能力。Agent = Function Calling + 循环 + 决策逻辑。

**主流 LLM 的 Function Calling 支持：**
- OpenAI：`tools` 参数，最成熟
- Anthropic Claude：`tool_use` 功能
- 开源模型：通过特定 prompt 格式模拟（效果参差不齐）

---

### 2.4 Fine-tuning（微调）

**一句话：** 在预训练好的大模型基础上，用你自己的数据继续训练，让它更适应特定任务。

**什么时候需要微调：**
- Prompt 工程搞不定的场景（输出格式要求极严格、领域术语太多）
- 需要模型学会特定的"风格"或"行为模式"
- 想用小模型达到大模型在特定任务上的效果（省钱）

**什么时候不需要：**
- RAG 能解决的知识问题 → 用 RAG
- 简单的格式要求 → 用 Prompt 工程
- 通用能力 → 直接用大模型

**常见微调方法：**
- **Full Fine-tuning**：全参数微调，效果最好但成本最高
- **LoRA / QLoRA**：只训练一小部分参数，成本低很多，目前最主流
- **RLHF / DPO**：基于人类反馈的强化学习，用于对齐（让模型更听话）

> **对后端开发者来说：** 微调通常不是你的主要工作，但你需要理解它的原理和适用场景，面试时能说清楚"什么时候该用 RAG、什么时候该微调"就够了。

---

### 2.5 Prompt Engineering（提示工程）

**一句话：** 通过精心设计输入给 LLM 的文本（prompt），来控制输出质量和格式。

**常用技巧：**

| 技巧 | 说明 | 示例 |
|------|------|------|
| **System Prompt** | 设定角色和行为规则 | "你是一个 Python 专家，只用中文回答" |
| **Few-shot** | 给几个示例让模型学格式 | "输入：xxx → 输出：yyy" |
| **Chain of Thought** | 让模型一步步推理 | "请一步步思考后再给出答案" |
| **Output Format** | 指定输出格式 | "请以 JSON 格式返回，包含 name 和 score 字段" |
| **Constraint** | 设定约束条件 | "如果不确定，请回答'我不知道'，不要编造" |

**这不是一个独立的技术方向，而是所有 AI 应用开发的基本功。**

## 3. 主流框架和工具（编排层）

### 3.1 LangChain

**定位：** 最流行的 LLM 应用开发框架，Python / JS 双语言支持。

**它做什么：**
- 封装了各种 LLM 的调用接口（OpenAI、Anthropic、本地模型...）
- 提供 RAG 的全套组件（文档加载、切分、向量存储、检索）
- 提供 Agent 框架（工具定义、执行循环）
- Chain（链）：把多个步骤串起来

**优点：** 生态最大，教程最多，什么都能做
**缺点：** 抽象层太多，代码难调试，过度封装，性能一般

**面试态度：**
> 了解 LangChain 的设计思路，但项目中选择手写核心逻辑而不是直接依赖它，因为：1）更好理解底层原理 2）更灵活可控 3）减少不必要的依赖。这个回答面试官会很喜欢。

```python
# LangChain 风格（高度封装）
from langchain.chains import RetrievalQA
qa = RetrievalQA.from_chain_type(llm=llm, retriever=retriever)
result = qa.run("什么是 Docker？")

# 手写风格（你现在的项目）
chunks = retrieval_service.search(query, top_k=5)
if has_sufficient_evidence(chunks):
    answer = llm_service.generate(query, chunks)
```

### 3.2 LlamaIndex

**定位：** 专注于数据索引和检索的框架，RAG 场景比 LangChain 更专业。

**它做什么：**
- 各种数据源的连接器（PDF、网页、数据库、API...）
- 多种索引结构（向量索引、关键词索引、树形索引、知识图谱索引）
- 高级检索策略（子问题分解、递归检索、融合检索）

**和 LangChain 的区别：**
- LangChain 是"什么都做的瑞士军刀"
- LlamaIndex 是"专精 RAG 的手术刀"

**适用场景：** 如果你的项目核心是知识检索和问答，LlamaIndex 比 LangChain 更合适。

### 3.3 Dify / FastGPT / Coze

**定位：** 低代码 / 无代码的 AI 应用搭建平台。

**它们做什么：**
- 可视化拖拽搭建 AI 工作流
- 内置 RAG、Agent、对话管理
- 提供 API 接口，可以直接部署

**对你的意义：**
- 了解它们的设计思路，但不要用它们做简历项目
- 面试官想看的是你能自己实现这些能力，而不是会用平台

### 3.4 CrewAI / AutoGen / MetaGPT

**定位：** 多 Agent 协作框架。

**核心思路：**
- 定义多个 Agent，每个有不同的角色和能力
- Agent 之间可以对话、协作、分工
- 适合复杂任务的自动化

```
例子：自动写一篇技术博客
  - 研究员 Agent：搜索资料、整理要点
  - 写手 Agent：根据要点写初稿
  - 审稿 Agent：检查事实准确性和文笔
  - 编辑 Agent：最终润色和排版
```

**现阶段建议：** 了解概念就行，多 Agent 系统目前还不太成熟，单 Agent 做好已经很有价值了。

## 4. 基础设施层

### 4.1 向量数据库

**干什么的：** 存储和检索向量（embedding），是 RAG 的核心基础设施。

**主流选择：**

| 数据库 | 特点 | 适用场景 |
|--------|------|----------|
| **Chroma** | 轻量、嵌入式、Python 原生 | 本地开发、小项目（你现在用的） |
| **Milvus** | 分布式、高性能、功能全 | 生产环境、大规模数据 |
| **Pinecone** | 全托管云服务、零运维 | 不想自己运维的团队 |
| **Weaviate** | 支持混合搜索（向量+关键词） | 需要多种检索方式 |
| **Qdrant** | Rust 写的、性能好 | 对性能有要求的场景 |
| **pgvector** | PostgreSQL 插件 | 已有 PG 基础设施、数据量不大 |
| **FAISS** | Meta 开源的向量检索库（不是数据库） | 纯检索、不需要持久化管理 |

> **面试建议：** 至少深入了解你用的那个（Chroma），能说清楚 HNSW 索引的基本原理，知道向量检索的时间复杂度和 trade-off。

### 4.2 Embedding 模型

**干什么的：** 把文本变成向量。

**主流选择：**
- **all-MiniLM-L6-v2**：轻量、速度快、效果够用（你现在用的）
- **bge-large-zh**：中文效果好，智源出品
- **text-embedding-3-small/large**：OpenAI 的，效果好但要花钱
- **GTE / E5 系列**：阿里/微软出品，多语言效果好
- **Cohere embed-v3**：多语言、支持不同检索类型

> **选型原则：** 中文场景优先考虑 bge 系列；英文或多语言用 E5/GTE；预算充足用 OpenAI；本地部署用 sentence-transformers。

### 4.3 推理引擎 / 模型服务

**干什么的：** 把大模型跑起来，提供 API 服务。

- **vLLM**：目前最主流的开源推理引擎，支持 PagedAttention，吞吐量高
- **Ollama**：本地跑模型最简单的方式，一行命令启动
- **TGI（Text Generation Inference）**：HuggingFace 出品
- **SGLang**：新兴的高性能推理框架

> **对后端开发者来说：** 你不需要自己部署推理引擎（除非面试要求），但要知道它们的存在和基本原理。面试时能说"生产环境可以用 vLLM 部署开源模型，通过 OpenAI 兼容接口调用"就够了。

## 5. 几种技术模式的对比和选型

### 5.1 什么时候用什么

```
用户问题 → 需要外部知识吗？
  ├─ 不需要 → 直接调 LLM（Prompt Engineering）
  └─ 需要 → 知识是静态的还是动态的？
       ├─ 静态文档 → RAG
       ├─ 需要实时查询 → Function Calling / Agent
       └─ 需要多步骤操作 → Agent
```

### 5.2 RAG vs Fine-tuning vs Prompt Engineering

| 维度 | Prompt Engineering | RAG | Fine-tuning |
|------|-------------------|-----|-------------|
| **成本** | 最低 | 中等 | 最高 |
| **实现难度** | 低 | 中 | 高 |
| **知识更新** | 改 prompt 即可 | 更新知识库即可 | 需要重新训练 |
| **适用场景** | 格式控制、简单任务 | 知识问答、文档检索 | 风格迁移、领域适配 |
| **幻觉控制** | 一般 | 好（有来源） | 一般 |

> **面试万能回答：**
> 优先用 Prompt Engineering 解决；搞不定再上 RAG（知识类问题）或 Fine-tuning（行为类问题）；最复杂的场景可能需要 RAG + Fine-tuning 结合。

## 6. 和后端开发的结合点

作为后端开发者做 AI 应用，你的核心竞争力不是模型本身，而是：

### 6.1 你能做的（也是面试官想看的）
- **API 设计**：RESTful / GraphQL 接口设计，流式响应（SSE/WebSocket）
- **数据管道**：文档处理、清洗、切分、索引的工程化
- **检索优化**：多路召回、重排序、缓存策略
- **系统设计**：高并发、限流、降级、监控
- **Agent 调度**：状态管理、工具编排、错误恢复
- **部署运维**：Docker、CI/CD、日志、可观测性

### 6.2 面试常见问题方向
1. "你的 RAG 系统检索效果怎么评估的？" → 需要有评估指标和数据
2. "chunk 大小怎么确定的？" → 需要有实验对比，不是拍脑袋
3. "如果文档量从 100 篇变成 100 万篇，架构怎么调整？" → 需要懂分布式检索
4. "LLM 调用超时了怎么办？" → 降级策略、缓存、重试
5. "怎么防止 prompt 注入？" → 输入过滤、角色隔离、输出校验

## 7. 学习路径建议

```
第一阶段：基础（1-2 周）
  ✓ 理解 RAG 全流程（你已经做到了）
  → 理解 Embedding 和向量检索原理
  → 理解 Function Calling 机制

第二阶段：进阶（2-4 周）
  → 实现一个 Agent（ReAct 循环 + 工具调用）
  → 了解主流框架的设计思路（LangChain、LlamaIndex）
  → 学习评估方法（检索评估 + 生成评估）

第三阶段：工程化（持续）
  → 流式输出、并发处理、缓存优化
  → 监控和可观测性
  → 生产环境部署和运维
```

## 8. 术语速查表

| 术语 | 全称 | 一句话解释 |
|------|------|-----------|
| LLM | Large Language Model | 大语言模型，如 GPT-4、Claude |
| RAG | Retrieval-Augmented Generation | 先检索再生成，减少幻觉 |
| Embedding | - | 把文本变成向量 |
| Vector DB | Vector Database | 存储和检索向量的数据库 |
| Chunk | - | 文档切分后的片段 |
| Token | - | LLM 处理文本的最小单位，约 0.75 个英文单词或 0.5 个中文字 |
| Context Window | - | LLM 一次能处理的最大 token 数 |
| Hallucination | - | 幻觉，LLM 编造不存在的信息 |
| Grounding | - | 让 LLM 的回答基于真实来源 |
| ReAct | Reasoning + Acting | Agent 的核心循环：思考→行动→观察 |
| Function Calling | - | LLM 以结构化方式请求调用外部函数 |
| Fine-tuning | - | 在预训练模型上用自己的数据继续训练 |
| LoRA | Low-Rank Adaptation | 低成本微调方法，只训练少量参数 |
| RLHF | Reinforcement Learning from Human Feedback | 基于人类反馈的强化学习 |
| CoT | Chain of Thought | 链式思考，让模型一步步推理 |
| Few-shot | - | 在 prompt 中给几个示例 |
| Zero-shot | - | 不给示例，直接让模型做任务 |
| Reranker | - | 对初步检索结果重新排序的模型 |
| BM25 | Best Matching 25 | 经典的关键词检索算法 |
| HNSW | Hierarchical Navigable Small World | 主流的近似最近邻搜索算法 |
| SSE | Server-Sent Events | 服务端向客户端推送流式数据 |
| MCP | Model Context Protocol | Anthropic 提出的模型上下文协议 |
