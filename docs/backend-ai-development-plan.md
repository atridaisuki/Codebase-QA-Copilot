# Codebase QA Copilot 开发计划（后端 + AI 应用方向）

## 1. 项目定位

这个项目后续不应该继续往“纯 demo”方向发展，而应该明确定位为：

> **一个基于 FastAPI + 向量检索 + LLM 的文档问答后端服务，重点体现后端工程能力和 AI 应用工程能力。**

也就是说，这个项目要同时体现两类能力：

### 后端能力
- API 设计
- 配置管理
- 错误处理
- 日志
- 测试
- 容器化
- 数据持久化
- 异步任务

### AI 应用能力
- 文档 ingest
- chunking
- embedding
- retrieval
- grounded answer
- no-answer 策略
- 评测意识
- prompt injection / 安全边界

---

## 2. 总体开发原则

### 原则一：先工程化，再炫技
优先补：
- Docker
- 日志
- 错误处理
- 测试
- 配置
- 数据持久化

不要优先做：
- 多 agent
- 复杂 planner
- 花哨前端
- 过重抽象

### 原则二：先把单服务做稳，再谈复杂 Agent
当前这个项目更适合作为：
- **后端 + RAG 应用**

而不是一上来做：
- 多智能体平台

### 原则三：每一阶段都要能写进简历
每次开发都优先考虑：
- 面试怎么讲
- 简历怎么写
- 能证明什么能力

### 原则四：边投递边迭代
这个项目不需要“全部做完再投”，而是：
- 先形成可讲版本
- 再逐步补强

---

## 3. 分阶段开发路线

## Phase 1：从“能跑”升级到“像个认真项目”

### 目标
先把项目打磨成一个 **可展示、可运行、可讲解** 的后端 + AI 项目。

### 重点内容
1. 完善 README
2. 完善 docs
3. 补 `.env.example`
4. 补运行说明 / 测试说明
5. 补 Dockerfile
6. 补 lint / type check

### 建议实现项
- `Dockerfile`
- 可选：`docker-compose.yml`
- `ruff`
- `pytest`
- `mypy` 或 pyright
- 更清晰的环境变量说明

### 这一阶段的价值
这是投入最小、回报最高的一步。完成后你就可以在简历里说：

- 项目支持容器化运行
- 有基础测试与质量检查
- 文档完整、结构清晰

### 简历可写点
- 基于 FastAPI、Chroma 和 Claude 实现文档问答服务
- 支持容器化部署和本地开发环境配置
- 补充测试、文档和工程化基础设施，提升项目可维护性

---

## Phase 2：把单机 Demo 升级成“稳定后端服务”

### 目标
让这个项目不仅能跑，而且：
- 出错时能定位
- 接口行为清晰
- 配置行为稳定

### 重点内容
1. 统一错误处理
2. 统一日志
3. 请求级日志 / 检索日志 / LLM 日志
4. 明确 HTTP 状态码语义
5. 配置分层

### 建议实现项
- 全局异常处理器
- 统一错误响应结构
- request id / trace id
- retrieval 耗时日志
- LLM 调用失败日志
- config 按 dev/test/prod 分层

### 这一阶段的价值
这是典型后端项目能力。而且 AI 项目里，日志尤其重要，因为：
- 检索质量问题要排查
- 模型调用失败要排查
- grounded / no-answer 误判要排查

### 简历可写点
- 设计统一异常处理与日志链路，提升接口稳定性和问题排查效率
- 增加检索和模型调用日志，支持 AI 问答质量分析

---

## Phase 3：把 RAG 做到“更像真实 AI 应用”

### 目标
把当前 Retrieval V2 继续打磨成一个 **有质量意识的 AI 应用系统**。

### 重点内容
1. 完善 retrieval 后处理
2. 优化 citation / snippet 展示
3. 做小型评测集
4. 加入失败样例分析
5. 记录 v1/v2 效果差异

### 建议实现项
- snippet 命中位置优化
- source 展示优化
- 人工构建 20~30 条评测样本
- 评测脚本
- retrieval 结果对比文档
- grounded / no-answer 准确性观察

### 这一阶段的价值
这一步是“AI 应用工程感”的核心。很多项目只做到：
- 能问
- 能答

但更好的项目会做到：
- 知道什么时候该答
- 知道什么时候不该答
- 知道优化是否真的有效

### 简历可写点
- 设计 grounded / no-answer 机制，降低无依据回答
- 构建小规模评测集，对 retrieval 优化效果进行验证
- 通过 score 过滤、chunk 合并、上下文预算控制提升回答稳定性

---

## Phase 4：补齐“后端系统味道”

### 目标
让项目从“AI demo”更进一步，变成 **真正的后端 + AI 服务原型**。

### 重点内容
1. 增加关系数据库
2. 保存业务数据
3. 加简单鉴权
4. 支持多用户/多会话雏形

### 建议实现项
- PostgreSQL
- 文档元数据表
- ingest 任务记录表
- 查询日志表
- API key 或 JWT
- 简单用户隔离

### 为什么要做
因为只靠 Chroma 不够像完整系统。真实系统还要保存：
- 用户
- 会话
- 任务
- 文档元数据
- 审计日志

### 这一阶段的价值
这一步会明显增强你的“后端”标签。

### 简历可写点
- 引入 PostgreSQL 保存文档元数据、任务记录和查询日志
- 增加基础鉴权能力，为多用户访问和资源隔离提供支持

---

## Phase 5：把长任务处理做成更真实的服务

### 目标
把 ingest 从同步流程升级为 **可查询状态的异步任务**。

### 重点内容
1. ingest 异步化
2. 长任务状态查询
3. 失败重试或失败可见

### 建议实现项
- Celery / Dramatiq / RQ 三选一
- `/ingest` 改为提交任务
- `/tasks/{id}` 查询状态
- 失败日志和错误原因记录

### 为什么值得做
这一步很像真实业务：
- 文档解析可能慢
- embedding 可能慢
- 重建索引不是瞬时完成

这也是后端面试里很好讲的“为什么要异步化”的例子。

### 简历可写点
- 将文档 ingest 流程改造为异步任务，支持状态查询与失败可观测
- 提升长时任务处理能力和服务稳定性

---

## Phase 6：补 AI 应用安全与边界控制

### 目标
让项目具备更像真实 AI 系统的安全意识。

### 重点内容
1. prompt injection 风险说明
2. 工具边界意识
3. 输出约束
4. 高风险操作确认机制思维

### 建议实现项
- docs 中增加安全说明
- 对外部内容与系统指令做边界隔离说明
- 增加基础输入长度限制 / 文档类型限制
- 为未来 tool use 预留权限思路

### 为什么重要
现在 AI 应用岗位越来越看：
- 你知不知道 prompt injection
- 你知不知道工具滥用风险
- 你会不会把外部内容直接当系统指令

### 简历可写点
- 增加 grounded 约束与 no-answer 策略，降低幻觉和无依据输出风险
- 具备 prompt injection 与工具边界控制的基础安全意识

---

## 4. 当前阶段最优先做的 3 件事

如果当前是 **边投边补**，不建议一次铺太大。最优先做这 3 件事：

### 第一件：Docker
原因：
- 快
- 好讲
- 简历立刻加分

### 第二件：日志 + 统一错误处理
原因：
- 很后端
- 很工程
- 很适合面试追问

### 第三件：小型评测集
原因：
- 很 AI 应用
- 很体现“不是瞎调 prompt”
- 很适合讲 Retrieval V2 的价值

---

## 5. 暂时不建议优先投入的方向

当前阶段先别把时间砸在这些地方：

- 多 agent 编排
- planner-executor 重架构
- 很复杂的前端页面
- 过重的监控平台
- 很深入的 reranker 接入
- 自研 Agent 框架

原因很简单：

> 这些东西不一定最能提升你的求职竞争力，反而会分散你补后端 + AI 核心能力的时间。

---

## 6. 最适合当前阶段的路线总结

### 短期目标
把项目打磨成：
- **能运行**
- **能讲**
- **能写进简历**
- **有一点工程化**
- **有一点 AI 评测意识**

### 中期目标
把项目升级成：
- 有 Docker
- 有日志
- 有错误处理
- 有测试
- 有小评测集
- 有 retrieval 优化说明

### 后期目标
再逐步变成：
- 有鉴权
- 有 PostgreSQL
- 有异步任务
- 有更完整的数据链路管理

---

## 7. 一句话版本

> **这个项目后续的正确开发方向，不是做成“炫的 agent demo”，而是做成“能体现后端工程能力 + AI 应用工程能力”的 RAG 后端服务项目。**
